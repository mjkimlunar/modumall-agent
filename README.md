# 모두몰 고객응대 에이전트 — 소스 코드

고객 문의 한 줄을 받아 **분류하고 → 어드민에서 조회하고 → 상담원 업무 매뉴얼에 근거해 답하는**
에이전트입니다. 고쳐 가며 실험하기 좋게 파일을 나눠 두었습니다.

## 5분 만에 시작하기

```bash
pip install -r requirements.txt
cp .env.example .env        # 그리고 OPENAI_API_KEY 를 채우세요
set -a; . ./.env; set +a    # (Windows PowerShell: $env:OPENAI_API_KEY="sk-...")

python evaluate.py          # 두 지표를 잰다  ← 여기서 시작
python chat.py              # 직접 말 걸어 본다
```

데이터는 없으면 자동으로 받습니다.

## 이 프로젝트를 쓰는 방법

**한 군데 고치고 → `python evaluate.py` → 숫자가 어디로 움직였나 본다.** 이 한 바퀴가 전부입니다.

`evaluate.py` 는 점수만 찍지 않고 **오분류 목록과 실패 사례를 함께 출력합니다.** 점수보다 그 아래
목록이 중요합니다. 무엇을 고쳐야 할지가 거기 적혀 있습니다.

## 파일 지도 — 어디를 고치면 무엇이 움직이나

| 파일 | 무엇이 들어 있나 | 고치면 움직이는 것 |
| --- | --- | --- |
| `config.py` | 모델·임계값·동시 호출 수 | 둘 다. 가장 싸게 실험해 볼 수 있는 곳 |
| **`prompts.py`** | 라우팅 지침 · 답변 규칙 | **둘 다. 가장 크게 움직인다** |
| `router.py` | 분류 그래프 (`classify` · `gate`) | ① 의도 분류 |
| `tools.py` | 조회 도구 9개 (`search_product` 포함) | ② 답변 — 특히 `tools 미호출` |
| `context.py` | 매뉴얼 쪼개기 · 라우트별 컨텍스트 | ② 답변 — 근거가 프롬프트에 들어갔는가 |
| `answer.py` | 도구 호출 루프 (agent ↔ tools) | ② 답변 |
| `guardrail.py` | 답변 속 숫자의 출처 역추적 | ② 답변 — `forbid` |
| `agent.py` | 전체 파이프라인 그래프 | 흐름 자체 (되묻기·이관 경로) |
| `evaluate.py` | 두 지표 측정 | 채점 기준 자체를 고칠 때 |
| `chat.py` | 대화 CLI | — |

코딩 에이전트(Claude Code, Cursor 등)에 이 폴더를 열어 두고 고칠 곳을 지정해 시키면 됩니다.
**무엇을 시키든 "고치고 나서 `python evaluate.py` 로 다시 재 줘"를 붙이세요.**

## 지켜야 할 것 세 가지

**평가셋(`split == "eval"`)은 절대 프롬프트에 넣지 마세요.** 예시는 `fewshot` 40건에서만 가져옵니다.
평가 문항을 넣으면 점수는 오르지만 그 점수는 거짓말이 됩니다.

**한 번에 하나만 바꾸세요.** 둘을 동시에 바꾸면 올랐어도 뭐 때문인지 모릅니다.

**바꾼 것과 숫자를 기록하세요.** 세 번쯤 지나면 "뭐가 제일 좋았더라"를 기억으로 더듬게 됩니다.

| # | 바꾼 것 | 분류 정확도 | 답변 통과율 | 메모 |
| --- | --- | --- | --- | --- |
| 0 | 그대로 | | | 기준선 |
| 1 | | | | |

## 알아 두면 좋은 것

**숫자는 실행마다 조금씩 다릅니다.** LLM 호출이라 그렇습니다. 큰 변화가 아니면 **두 번 재 보고**
판단하세요.

**전체 측정에 3~4분, 호출 300건쯤 듭니다.** 라우팅만 보려면 `--only router` 를 쓰세요(1분).

**`config.py` 의 `WORKERS`** 는 동시 호출 수입니다. 요청 한도(rate limit) 오류가 나면 낮추세요.

**도구를 고쳤으면 한 번 호출시켜 보세요.** 선택 인자를 `Optional[int] = None` 이 아니라
`int = None` 으로 적으면 모델이 `None` 을 보냈을 때 스키마 검증에 걸려 왕복이 낭비됩니다.
`python chat.py "캔버스화 배송비 얼마예요?"` 로 도구가 제대로 불리는지 바로 확인할 수 있습니다.

# 개선 작업 기록 (2026-09-16)

원본 코드에서 출발해 두 지표를 올린 작업의 설계 근거를 남깁니다. **`evaluate.py` 는 대회 규칙상
수정하지 않았습니다** — 채점기의 한계는 고치는 대신 `report_scoring_limits.py` 로 원본/보정
수치를 병기해 보고합니다.

## 결과

모든 지표는 **기준선·최종 각각 3회 측정 평균**입니다. 같은 입력도 ±9%p 흔들리므로 단일 측정은
쓰지 않았습니다.

| 지표 | 기준선 | 최종 |
| --- | --- | --- |
| ① 의도 분류 정확도 | 0.942 | **0.980** (오분류 7→2건) |
| ① macro F1 | 0.945 | **0.984** |
| ② 1턴 답변 통과율 | 57.3% | **77.1%** |
| 실제 고객 문의 40건 자동화율 | 7.5% | **12.5%** |
| 멀티턴 전체 통과율 (56턴 중 53턴 채점) | 미측정 | 약 68% (2차 턴이 1차보다 약 30%p 낮음) |
| 1회 호출 입력 토큰 | 5,024 | 약 6,600 |

관측 범위 — ① 기준선 0.942(3회 동일) / 최종 0.975~0.983, ② 기준선 53.1~59.4% / 최종
75.0~78.1%. 두 지표 모두 기준선과 최종의 범위가 겹치지 않습니다. 다시 잰 기준선은 강의
공표값(0.94 · macro F1 0.945 · 56%)과 일치합니다.

**되돌린 변경이 하나 있습니다.** 멀티턴 2건(지연 사유·가격 누락)을 고치려 `ANSWER_RULES`
3·7단계에 넣은 지시가 1턴 지표를 8%p 깎았습니다(68.8% vs 77.1%, 두 그룹의 측정 범위가 겹치지
않음). 멀티턴 점수도 나아지지 않아 되돌렸습니다 — 지시 하나가 어디까지 번지는지는 재봐야
압니다.

## 어떤 정책 조항이 어떤 코드가 되었는가

에이전트는 회사 규정을 대신 수행하는 존재이므로, 모든 판단 기준은 상담원 업무 매뉴얼에서
가져왔습니다. 개발자가 새로 발명한 기준은 없습니다.

| 매뉴얼 조항 | 요구 사항 | 구현 위치 |
| --- | --- | --- |
| §0 원칙 1 | 공통 정책은 즉답, 건별 값은 조회 후 안내 | `context.FIXED_POLICY` · `ANSWER_RULES` 절대규칙 1·2 |
| §0 원칙 2 | 주문 상태는 조회 없이 단정 금지 | `ANSWER_RULES` 절대규칙 3 · 4단계 |
| §0 원칙 3 | 모르면 모른다고 하고 넘긴다 | `router.gate()` `CONF_THRESHOLD=0.5` |
| §1 | 상담을 4개 유형으로 분류 | `ROUTE_GUIDE` 라우트 정의 (+ §7.1에서 `OTHER`) |
| §1.1 | 쓴 단어가 아니라 원하는 결과로 판단 | `ROUTE_GUIDE` 분류 원칙 + 경계 예시 5종 |
| §1.2 | 분류 우선순위 (범위밖 > 이관 > 진행중 반품) | `ROUTE_GUIDE` 분류 우선순위 |
| §2.3 | 주문 제작 상품은 반품 불가, 접수 시 선제 안내 | `ANSWER_RULES` 5단계 단서 |
| §2.4 | 송장 출력 후 변경 불가 → 반품 절차·비용까지 안내 | `ANSWER_RULES` 5단계 · `context.SECTION_MAP` (ORDER_PLACE 에 5장 추가) |
| §2.5 | 재입고 예정일은 확정된 경우만 안내 | `ANSWER_RULES` 3단계 · `tools.get_restock_info` |
| §3.2 | 사이즈 표기 차이는 무료 반품 사유 아님(고객 부담) | `ANSWER_RULES` 9단계 (가) |
| §3.4 | 상세페이지 오표기는 무료 반품 대상 | `ANSWER_RULES` 9단계 (나) |
| §4.2 | 무료배송 기준액은 카테고리·상품별 조회 | `tools.get_shipping_policy` · `guardrail` 툴 미호출 단정 검사 |
| §4.3 | 출고 마감 11시, 단 주문 제작은 2~5영업일 추가 | `ANSWER_RULES` 0단계 주의 |
| §4.4 | 지연 시 사유(택배사 물량 집중 등) 고지 | `ANSWER_RULES` 7단계 |
| §4.5 | 당일배송은 지역 확인 후 비용 안내 | `tools.region_info` · `ANSWER_RULES` 0단계 |
| §5.1 | 카테고리별 반품 기간, 하자·오배송은 기간 무관 | `tools.get_return_policy` · `ANSWER_RULES` 7단계 |
| §6.1 | 반품 배송비 전체 5,000원 / 부분 2,500원 | `context.FIXED_POLICY` · `ANSWER_RULES` 9단계 (가) |
| §6.4 | 검품 전에는 귀책·배송비 부담 단정 금지 | `ANSWER_RULES` 절대규칙 4 · `guardrail.check_pending_fields` |
| §7.1 | 응대 범위 밖 4유형은 안내 문구가 각각 다름 | `agent.node_escalate` → `answer_with_llm(route="OTHER")` |
| §7.2 | 동일 사안 3회 이상 반복 문의는 즉시 이관 | `router.gate()` `REPEAT_ESCALATE` |
| §8 | 존댓말 1~3문장, 불가 사항은 사유 먼저 + 대안 | `ANSWER_RULES` 절대규칙 6 |

## 지표에 잡히지 않지만 고친 것

정답셋 채점 경로를 지나가지 않아 두 지표 어디에도 반영되지 않지만, 실제 고객에게 나갈 답변의
오류였습니다. `chat.py` 로 직접 말을 걸어봐야 발견되는 종류입니다.

- **`OTHER` 응대 오안내** — 제조사 A/S 문의에 "주문하신 **사이트**의 고객센터로 문의하세요"라는
  틀린 안내가 나가고 있었습니다. `node_escalate` 가 §7.1 의 4개 유형을 하나의 고정 문자열로
  처리했기 때문입니다. 매뉴얼을 읽고 유형별로 답하게 고쳤고, 이미 조회한 결과가 있으면
  (외부 채널 주문 확인 등) 그 결과를 함께 넘겨 애매한 답이 되지 않게 했습니다.
- **§7.2 반복 문의 이관 누락** — 규정이 구현되어 있지 않았습니다. 분류가 아니라 정책 판정이므로
  `classify` 가 아닌 `gate()` 에 넣었습니다.
- **미확정(`null`) 필드 단정 환각** — 검품 전 `null` 을 "검품 완료·하자 판정·무료 처리"로
  단정하는 답변을 만들어 넣었더니 가드레일이 그대로 통과시켰습니다(숫자가 없어서).
  `guardrail.check_pending_fields` 를 추가했습니다.
- **멀티턴 문맥 혼동** — `with_history()` 가 고객 발화를 공백으로 이어 붙여, 모델이 어느 것이
  현재 질문인지 몰라 앞 턴 질문에 다시 답했습니다(3/3 회 재현, "기본 티셔츠는 구매 불가"라는
  사실과 반대되는 안내). `[이전 대화에서 고객이 한 말]` / `[지금 답해야 할 문의]` 로 구분하는
  형식으로 바꿔 0/3 이 됐습니다.

## 고치지 못한 것

- **데이터 스키마 한계** — `get_product_detail` 의 `stock` 은 전체 재고라 옵션별 품절을 알 수
  없고(`get_restock_info` 를 함께 부르게 해 우회), `get_order_status` 에 수령일이 없어
  "수령 후 N일 경과"를 계산할 방법이 없습니다.
- **엔티티 링킹** — 실제 문의의 77.5% 가 문장에 상품명 자체가 없어 되묻기로 빠집니다. 검색
  알고리즘이 아니라 로그인 고객의 주문 이력 같은 시스템 컨텍스트가 있어야 풀립니다.
- **채점기 구조 한계** — 도구를 호출하면 무조건 `ANSWER` 로 분류하므로 "조회 + 되묻기"가
  공존해야 하는 턴은 통과가 불가능합니다. 정규식으로 보정해 봤더니 오히려 81.2%→78.1% 로
  떨어졌습니다("주문 도와드릴까요?" 같은 정중한 마무리를 정보 요청으로 오인). 의미를 판정하는
  LLM-as-a-judge 가 필요합니다.
